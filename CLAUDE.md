# Velocity — working rules for any Claude session in this repo

Velocity is an AI-coach training app for endurance athletes (Ironman first). Owner: PR (GitHub `benalexkeller`,
project email benalexkeller@gmail.com). Live site: https://velocity-smoky-three.vercel.app (Vercel Hobby, deploys `main`).
Database + logins: Supabase project `hngrtoufmjauqdkhncbp`. Product decisions and history live in PR's Claude Project
"Iron Man" (docs `claude/accounts-v1.md`, `claude/phase2-build-log.md`, `claude/phase2-product-spec.md`).

## How PR works
- Explain everything in simple, non-technical language. PR is not a backend developer; he decides product, you run the commands.
- Copy rule for the app AND for replies: cold facts and to-dos, no motivational, "impactful" or feel-good statements anywhere.
- Design must match the approved mocks 1:1: white background, Inter (self-hosted), blue accent `#2459FE`, cards with soft shadow, no dark mode.
- No long dashes in anything the athlete reads: no "—" (use a comma or colon) and no "–"; ranges take a plain hyphen, numbers tight ("10:15-11:15", "15-17 mph"), dates spaced ("26 Oct - 1 Nov"). Stored text is cleaned on the way out by `plain()` in `src/lib/data/index.ts` (plan text, phases, notes) and in `CoachText`. Titles never end with a full stop.
- No separator glyphs in UI text: never "·", "•" or "|" between facts. Inside a component, put the second fact after a gap (`<span className="at">`, same size, normal weight, muted); inside a sentence, a comma. Nothing bold for emphasis. Chart units go on the tick labels ("4 h", "20 mi"), never as a lone letter near the axis.
- Verify with a screenshot or a scripted click-through before saying something works. `scripts/snapshot.js` renders the review mirror.

## Stack
Next.js 16 App Router (read `node_modules/next/dist/docs` before assuming APIs — `proxy.ts`, not middleware), TypeScript, plain CSS
with tokens in `src/app/globals.css`, no UI library. `npm run dev` → http://localhost:3000. `npx tsc --noEmit -p .` must be clean.

## Data model (read this before touching data)
- `src/lib/store.tsx` — `PlanProvider` / `usePlan()` is the only source of truth for pages. It loads once from a backend, keeps a working
  copy, writes every change straight back. Derives `weeks` (plan JSON → `buildWeeks`, or `virtualWeeks()` when the plan is empty),
  `phases`, `athlete` (`src/lib/athlete.ts`), `activities` (all) vs `counted` (excluded ones removed — analysis/volume/status use `counted`).
- `src/lib/backend.ts` — `LocalBackend` (no env vars: PR's seed data + browser storage) and `SupabaseBackend` (env vars set: the user's rows).
  Accounts are ON only when `NEXT_PUBLIC_SUPABASE_URL` + `NEXT_PUBLIC_SUPABASE_ANON_KEY` exist (`.env.example`).
- `src/lib/data/index.ts` — types, seed loaders, classification (`sportOf`, `intensityOf`), `buildWeeks`, `phasesOf`, load/compliance math.
- `src/lib/analysis.ts` — `createAnalysis(activities, weeks, {phases, body, athlete})`; use through `useAnalysis()` in components.
- `supabase/schema.sql` — the whole database; idempotent, paste into Supabase SQL Editor. RLS: users only see their own rows.
  `admin_emails` decides who is admin (currently benalexkeller@gmail.com).
- Seed files (`src/lib/data/seed/*.json`) are PR's real plan/activities/body data; never invent data. `seed/maps.json` = OpenStreetMap vector base maps (via the Garmin MCP's `get_area_map`, thinned by the scratch script) that `RouteMap` draws under routes; routes outside them use CARTO label-free tiles.

## Product rules already decided
- No daily readiness/recovery score; load/fatigue/form from work done. Coach proposes changes only in the Sunday review; the athlete decides.
- Dashboard: today's hero card + next two days, "+ Add manually" bubble, This week, Last activity, phase strip, pace + volume charts.
- Plan tab = command center: week grid 05:00–21:00 (scrollable 04:00–23:00), Move/Edit/Delete/Log/Add all work, road-to-race ramp chart.
- Activities: list with frozen header, white detail panel on the right, Exclude from analysis + Delete.
- New accounts: profile setup (basics + availability) → `/plan/new` plan builder (5 screens: goal, history, fitness, time, devices/strength; branches by event type) → 30-second build screen → plan. Rule-based generator `src/lib/plan/generate.ts` reads `src/lib/plan/rules.ts` (sourced coaching rules, shown under "How this plan is built"). Spreadsheet import (`importPlan.ts`, template CSV). Answers stored in `plans.intake`; "Plan settings →" rebuilds. Minimum plan length 4 weeks. The race lives in the builder, not the profile.

## Public site, coach, Garmin (branch `public-site`, 2026-10-27)
- `/` is the public front page (`src/app/page.tsx` + `landing.css`, screenshots in `public/landing/`). Signed-in athletes are sent to `/dashboard` by `proxy.ts`; the page renders without the app shell and without loading data.
- No beta signs anywhere: feedback lives in the account menu ("Send feedback"). Supplement names like "Beta-alanine" are fine.
- Coach: `POST /api/coach` → OpenRouter (`OPENROUTER_API_KEY`, `COACH_DAILY_CAP` 40). Multi-model (`src/lib/coach/models.ts`): each request sends a model list with OpenRouter fallback; questions = `~anthropic/claude-haiku-latest` then `~google/gemini-flash-latest` (DeepSeek removed 1 Nov 2026: Google's verification refuses apps whose AI provider may train on data), whole-plan reviews = `~anthropic/claude-sonnet-latest`, `~openai/gpt-latest`, `~google/gemini-pro-latest` (the `~…-latest` aliases follow each family's newest model). Env `COACH_MODELS` / `COACH_MODELS_STRONG` replace a list. The public pages say "works across the leading AI models"; keep that true. Order inside the route: fixed red-flag check (`src/lib/coach/safety.ts`, no model) → library search (`src/lib/coach/library.ts` over `library-data.ts` + the admin's `library` table rows) → model with instructions (`prompt.ts`) and the athlete's context (`context.ts`). Answers cite passages as `[L1]`; the rail shows them as superscripts with a Sources list. Plan changes come back as proposals (`coach_messages.proposal`, `status`, `sources`, `tier`; SQL `supabase/schema-coach.sql`); Accept applies them through the store. A whole-plan review never runs by itself: the model pitches it (`request_restructure` → proposal of kind `review`), the athlete clicks "Run the full review" (or the rail's "Review my plan"), then mode `restructure` sends every remaining week (`plan_all`) to the strong list. Admin page has a Library editor. Without a key the rule-based `coachReply` answers.
- Garmin through Junction (junction.com): `src/lib/integrations/junction.ts`; routes `/api/connect/garmin` (start), `/done` (return), `/disconnect`, `/sync` (pulls the last 90 days with the athlete's own session: the minimum setup needs only the Junction key), `/api/connect/status`, webhook `/api/webhooks/junction` (Svix signature, service-role writes; optional, for automatic updates). Routes come from `map.summary_polyline`. Admin page lists connections + webhook calls (`admin_integrations`, `admin_webhook_log`). Env in `.env.example`; SQL in `supabase/schema-integrations.sql`. Switched on by `WEARABLE_PROVIDER=junction` + `WEARABLE_API_KEY`.

- Public site = front page (`src/app/page.tsx`, `landing.css`) + product pages `/product/{train,nutrition,coach}` (`src/app/product/[slug]`, content in `src/lib/public/product.ts`, which also feeds the top-bar menus in `components/public/PublicNav.tsx`). - Calendar (2026-10-30): Profile → Calendar card (`components/account/CalendarCard.tsx`), Plan header badge (`components/plan/CalendarBadge.tsx`), auto-sync (`components/CalendarSync.tsx`, mounted in AppShell for accounts: sends every session from 14 days ago to race day, 2.5 s after any plan change, when a calendar is linked and the list fingerprint differs). Google Calendar uses one scope, `calendar.app.created`: Velocity makes its own "Velocity training" calendar and can only touch that calendar. Event ids derive from session ids (`eventIdOf`), so repeats never duplicate. Refresh token stored AES-GCM-encrypted (key from `GOOGLE_CLIENT_SECRET` or `CALENDAR_TOKEN_KEY`). Routes: `/api/connect/google-calendar` (+ `/callback`), `/api/calendar` (status), `/sync`, `/disconnect`, `/link`, public `/api/calendar/feed/<secret>.ics` (calendar link for Apple/Outlook, served through the `calendar_feed` SQL function). SQL `supabase/schema-calendar.sql`; env `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`. Test without Google: `node scripts/mock-google.js` and the GOOGLE_* URL overrides in `.env.example` / the script header. Nothing from Google (profile name/email/picture, calendar events) may ever go into the coach context or any AI request: Google Limited Use. Google Cloud lists `calendar.app.created` (and `calendar.events.freebusy`) as non-sensitive, so no Google review is needed; Calendar API enabled and the scope added under Data Access on 2026-10-30, table created the same day. "Show my other events" (optional, Profile → Calendar): asks Google additionally for `calendar.events.readonly` (sensitive: needs Google verification before more than 100 people, unverified screen until then) and `calendar.calendarlist.readonly`; `/api/calendar/events` reads the chosen calendars live for the week shown and never stores them; WeekGrid draws them as grey read-only blocks (`.wg-oe`), all-day ones under the date; where one meets a session, the session keeps the left 64 % (`.wg-ev.nar`). Never revoke an old Google token on reconnect: revoking withdraws the whole grant, including the new token.

- Email sender (2026-11-02, live and tested on production): Velocity's own Supabase email templates in `supabase/email-templates/` (reset, confirm sign-up, magic link, change email, invite). Their links go to `/auth/callback?token_hash=…&type=…&next=…` (server `verifyOtp`), so they work in any browser and on any device, unlike Supabase's default `{{ .ConfirmationURL }}` PKCE links. Sending through Resend as custom SMTP in Supabase (host smtp.resend.com, port 465, user `resend`, password = Resend API key, sender no-reply@velocityathletes.com); DNS records for Resend live in Vercel (velocityathletes.com uses Vercel DNS).

- Outlook and Apple Calendar (2026-11-02): Profile → Calendar has Google, Outlook and Apple in one card, each with its own Velocity training calendar. Google is unchanged (calendar_links, scopes under Google review: do not touch). Outlook: `lib/calendar/outlook.ts`, Microsoft Graph, "common" endpoint (personal and work accounts), scopes openid email offline_access Calendars.ReadWrite; refresh tokens rotate and the new one is stored (`openAccount().newSecret`). Routes `/api/connect/outlook` (+ `/callback`, cookie `vel_ocal`). - Small fixes (2026-10-30): every OpenRouter request sends `provider: { data_collection: "deny" }` (only AI providers that neither store prompts nor train on them; the privacy page promises it). Profile → Delete account: `POST /api/account/delete` deletes the Velocity training calendar at Google and revokes access, ends the Junction/Garmin connection, then calls the SQL function `delete_my_account()` (`supabase/schema-account.sql`, security definer: deletes the athlete's feedback rows and their auth user; every other table cascades). - Passwords (2026-11-01): every password box is `components/account/PasswordInput.tsx` (eye button shows / hides it; hidden again on submit so browsers still offer to save it). Forgot password: Sign in → "Forgot password?" → `resetPasswordForEmail` with `redirectTo /auth/callback?next=/auth/reset` → `/auth/callback` turns the link into a session (`?code=`, or `?token_hash=&type=` if the Supabase email template is changed to link there) → `/auth/reset` sets the new password with `updateUser`. A failed or reused link goes to `/login?error=reset&mode=forgot`. Supabase's built-in email sender only delivers to the project team's addresses (2 emails an hour), so reset emails reach real athletes only once a mail sender (custom SMTP, e.g. Resend) is set in Supabase → Authentication → Emails; until then the form says to write through Help. Test without Supabase: `node scripts/mock-supabase-auth.js` and `NEXT_PUBLIC_SUPABASE_URL=http://localhost:54321 NEXT_PUBLIC_SUPABASE_ANON_KEY=test`.

- Account switching (2026-11-01 fix): the backends read the user id from the live session on every call (`getSession`), never a remembered id, and Sign out does a full page load. Before, signing out and creating another account in the same tab sent the new account's writes with the old id, and Supabase refused them (403, "Could not save" on Setup). `scripts/mock-supabase-auth.js` refuses profile writes for another user's id, so this can be re-tested locally.
